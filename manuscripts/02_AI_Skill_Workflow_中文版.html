从经文与注疏到机器核验

一种 AI 与“skill”辅助的宗教人文经典论证研究流程

Jason Wu · ORCID：0009-0003-1682-6165
方法文章预印本 · v1.0 · 2026年10月4日

英文题目：From Scripture and Commentary to Machine-Checked Arguments: An AI- and Skill-Assisted Workflow for Research in Religious Humanities

完整中文对照稿。章节、表格、公式和文献序号与整理后的英文稿对应。本文的 skill 指提供给 AI 助手的书面研究指令及配套参考材料。

摘要

AI 助手可以协助研究者整理资料、起草形式证明，但解释流畅和证明能够编译，都不足以证明某种解释忠实于文本。本文介绍在《楞严经》七处征心 Lean 重建项目中形成的一套研究流程。书面的 skill 规定了资料核对、解释承诺的区分、连接前提的人类审阅、条件形式化，以及研究成果的同步输出。一段有记录的共同“不二”读法研究对话，展示了这一过程：最初从独立性出发的表述，因为部分经文明说依赖条件而被修订；最终形式化关注的是实体化的认定，而不是因果上的独立性。本案例展示，人的纠正可以如何落实到谓词设计、定理范围、反模型和发表时的表述。带时间戳的记录与源码快照，使这段过程能够接受检查。这是一份描述性的单案例方法报告，不确立 AI 辅助或 skill 的因果效果，也不证明准确率或效率提升。它的贡献是提供一种实用的责任分配方式，区分文本证据、人类解释、AI 辅助和证明核验。

关键词： AI 辅助人文研究；研究流程；Lean；计算诠释学；可审计性；佛教研究；研究溯源

1. 为什么需要研究流程

AI 助手可能为某个宗教论证生成令人信服的解释，却忽略歧义词或未明说的前提。它也可能生成能够编译的 Lean 代码，只因为实质上已经把所需结论当成了假设。这是两个不同问题：文本忠实度与推理有效性，不能用同一种检查来评估。

本案例讨论中文《楞严经》《大正藏》T19、第945号卷一中关于心之所在的七段问答。前期项目用七个局部 Lean 模块重建了选定论证。后续对话则追问，是否可以通过一个共同原则理解它们。困难不在于漫长的证明搜索，而在于决定共同原则究竟意味着什么，各段是否支持拟议的连接，以及得到的定理是否回答了原来的问题。[1, 2]

计算诠释学已经为协调形式论证分析与解释修订提供了先例。[3] 本报告关注，当 AI 助手和可复用的书面指令包参与时，如何具体实施这种协调。Lean 检查形式化的证明项，不裁定文献学问题或宗教权威。[4]

2. 本研究中的“skill”是什么意思

本项目的 skill 是一份本地 Markdown 指令文档，即 sutra-argument-lean/SKILL.md，配有项目背景与流程参考材料。作者在私人研究档案中保留了这些指令的带日期副本。它告诉助手需要收集什么材料、如何区分证据与重建，以及应当完成哪些检查和交付。指令文档本身不是训练好的模型或证明检查器；实际检查由 Lean 和独立脚本执行。

其中的核心要求是具体的。摘录应附带连续经文语境。引文应保留繁体字和定位。注疏应注明出处，不能混入经文而不加区分。缺失的连接应与研究者讨论。教义假设应作为定理参数公开出现，而不是隐藏成全局公理。编译、依赖检查和范围检查应如实报告。研究札记、代码和教学说明，应描述同一条选定的论证。

项目的指导原则也限定了输出目标：论证可以在明确条件下排除某个主张，但本项目不尝试定义佛或如来藏。机器核验与宗教修证的完成，不被视为同一件事。

skill 所期望的价值在于流程：使遗漏更容易被察觉，也使中断后的工作更容易接续。助手是否遵循指令，仍然是一个需要观察的问题。本案例没有比较使用与不使用 skill 的研究，因此不能量化它的效果。

3. 一套责任分明的研究流程

下面五步从资料选择走向可审阅的成果。解释上的异议可能让研究者返回前一步，因此它不是只运行一遍的自动化流程。

3.1 确定文本单元

从完整问答开始，而不是从孤立结论开始。记录版本、卷号、页栏行位置及任何文字规范化处理。本项目从所保存的 CBETA 转录本中保留了连续段落。注疏工作副本则按 PDF 物理页或文档段落建立索引。这些定位有助于审阅，但不能被误认为所有版本都通用的固定页码。

AI 可以帮助检索段落、对齐版本并提出概要。研究者必须判断，选定的上下文是否充分，引文或归属是否忠实。使用过某份现代注疏，并不意味着需要在成果中重新分发其全文。

3.2 先用日常语言写出论证

引入符号之前，先描述所提主张、针对它的追问，以及通向矛盾所需的连接。一个词的不同含义应当分开。在这个案例中，“内”“合”“有所指”“相”“无著”等词，不能不加检查地在七处中都赋予同一种含义。

一种有用的成果是简短的前提台账。每项记录前提名称、文本出处或解释理由，以及它的地位：明文措辞、注疏支持的读法，还是研究者补充的连接。简短说明还应交代这项前提不主张什么。例如，在某一模型中把在外与不能相知联系起来，不等于提出一条反对远距离相互作用的普遍定律。

3.3 在把代码当作证据之前处理异议

助手提出重建方案；研究者用经文和原来想问的问题来检查它。解释发生变化时，可能需要修改定理目标，而不只是修补证明。这正是人的分歧能够发挥作用的地方：它决定代码究竟有没有表示所要研究的论证。

这个阶段的终点是明确陈述的条件主张，而不是对所有形而上问题达成一致。尚未解决的替代读法应继续列出。随后可以为一条选定路线编写证明，而不声称其他路线已经被排除。

3.4 编码并检查条件推导

把已经审阅的重建转为命题和显式假设。使用有说明性的名称，但要交代：命名本身不会把预期语义带进内核。应避免把所需结论直接重述为前提，除非这正是公开说明的研究对象。

编译实际文件，检查定理依赖，并检查是否存在未完成的证明。如果一个定理报告没有额外公理，还应另行查看它的参数：空的公理列表不意味着定理没有假设。读者应能在日常语言解释、Lean 定理签名和前提台账中，看见同一条连接。

3.5 检查范围并整理成果

尝试让各项前提在不矛盾的情况下同时成立。删除一项实质前提，寻找反模型。检查更强的结论是否也能推出，还是仍然缺乏支持。对于有限命题模型，穷举是一项适度且可复核的辅助。它审计的是提供给脚本的公式，因此，这些公式与预期 Lean 模型是否一致，也是需要审阅的一项责任。

最后，发表时应将各层材料一并提供：经文与注疏出处、解释、显式前提、源码、工具链、检查结果和范围说明。教学页面可以简化展示，但仍应保留查看假设的入口。展示出来的每项证明状态，都应对应一次实际运行，并能确定运行所用的源码版本。

这一纠正具有实质性。把心描述为依条件而生，并不意味着它在因果上独立于这些条件。修订后的共同谓词关注一种实体化的认定：将与对象相对、被另立的能知者，认作对话所求的心性。随后，项目提供一个共同排除条件和七条逐段连接。定理证明，在这些假设下，每个描述及其相应心性认定不能同时成立。

该定理并不单独反驳描述本身。认清这一点，还需要第二个区分：共同层针对的语境认定，并不自动等于每个原有局部模块中的主张。实现提供一个带显式连接前提的转接定理，而不悄悄替换此前七个证明。

这一序列展示一条可行的反馈过程：文本异议 → 修订解释 → 修订谓词 → 精确结论 → 范围见证。它不表明 AI 独立发现了某项佛教教义。有记录的人类贡献与所查阅的注疏，都是说明该形式化如何形成的组成部分。

5. 这些检查确立了什么

共同模块包含8个定理声明，包括覆盖、排除、转接和范围见证。就单个章节而言，Description 表示选定的候选说法成立；Separated 表示这种说法把能知者实体化为与其对象相对、自存的存在；Identifies 表示该候选被正确认定为对话所寻求的心性。通常的功能区分，本身并不能确立 Separated。

基本排除推导使用两项显式前提：

U: Separated → ¬ Identifies
B: Description → Separated

它们合在一起推出 ¬ (Description ∧ Identifies)。这里 → 表示蕴含，¬ 表示否定，∧ 表示合取。Lean 检查这个条件推导；文本解释仍然需要论证。

独立的布尔审计检查这三个命题的8种赋值。其中恰好4种同时满足 U 与 B，而这4种中没有一种满足 Description ∧ Identifies。一个满足前提的赋值是 Description = true、Separated = true、Identifies = false。它保留描述，同时拒绝认定。进一步的检查删除共同排除或某条连接，使此前被排除的认定可以成立。针对七个章节，7个带索引的省略见证说明，在这个表述中七条连接为何分别不可缺少。

若要复核穷举，在 v1.0 源码仓库根目录运行 python tools/check_shared_nonduality.py。结果写入 audit/shared-nonduality-scope.json。随稿复核指南说明8个声明各自的作用，并列出另外执行的 Lean 构建与依赖检查。

这些检查处理的是内部相容性、逻辑后果，以及对选定假设的依赖。它们不确立某部注疏的真确性、某个术语的最佳翻译或某项教义的正确性，也不使项目变成“没有假设”。假设只是被变得可以检查了。

6. 常见失败方式与实际控制措施

失败方式 流程中可以检查的控制措施
把 AI 转述当作经文原话 保留连续经文和 CBETA 定位；将引文字符与原文比较，并记录规范化处理
把某部注疏当作全体传统的一致意见 记录注家、作品、卷或节、页或段落定位，并保留不同侧重
把重要前提藏在谓词名称中 补入日常语言定义和显式连接
把编译结果误当成文本验证 分别报告证明状态与解释状态
共同定理悄悄改变局部目标 写明转接条件，并保留两层形式化
前提不相容，使反驳变得平凡 给出满足前提组的模型
把“没有额外公理”报告成“没有假设” 除公理依赖外，也检查定理参数
把新扩展归到较早的归档版本 分别标识已发布基线和本地快照

即使证明很初等，这些措施仍然有用。其目的在于让修订过程可以追溯，尤其是当助手连续提出多种看似合理的解释时。记录被放弃的解释，可以说明某项设计决定；但不能把这份记录当作所有替代读法都已穷尽的证据。

7. 局限与后续研究方向

这只是一个项目和一段选定对话，不是受控评估。研究者参与了解释的生成与评价。没有独立评审组给忠实度打分，没有基线测量节省的时间，也没有通过对比有无 skill 的实验来分离其贡献。归档支持重建可见过程，不支持关于 AI 有效性的因果断言。

后续研究可以让若干读者处理同一个经文单元，比较普通笔记与前提台账流程，并询问后者是否有助于更精确地定位分歧。另一项研究可以比较同一段落的不同形式化，而不把达成一致视为唯一值得追求的结果。这些研究都需要事先定义忠实度、实用性和裁定程序。

当前的方法启示更有限，也可以立即采用：把资料核对、解释、证明检查和发表判断安排在不同步骤，并保留步骤之间如何过渡的记录。AI 可以跨步骤协助；书面的 skill 可以提醒助手遵守要求；Lean 可以检查指定的推理主张。这个主张是否值得用于解释文本，仍由研究者负责。
